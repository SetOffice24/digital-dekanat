# Цифровой деканат — общие правила для ИИ-агентов

Этот файл — единая точка входа независимо от модели и инструмента. Общаться с командой на русском. Требования одинаковы для всех агентов; роли распределяются по задаче, а не закрепляются за конкретной моделью.

## Начало работы

1. Сначала прочитать `docs/HANDOFF.md`: актуальное состояние, запуск, принятые решения, открытые задачи и особенности окружения.
2. Перед изменением функциональности свериться с `docs/00-tz.md` и текущим кодом.
3. Использовать документы по назначению:
   - `docs/HANDOFF.md` — актуальное состояние проекта; §7 — подводные камни окружения;
   - `docs/00-tz.md` — требования конкурса и критерии жюри;
   - `docs/01-research.md` — исследование и исходный состав разделов;
   - `docs/ARCHITECTURE.md` — исходный архитектурный замысел, частично устаревший;
   - `docs/process-log.md` — история работы, решений и ошибок ИИ (половина оценки жюри по критерию «нейротехнологии» — вести подробно);
   - `docs/test-accounts.md` — вымышленные тестовые аккаунты;
   - `docs/licenses.md` — лицензии сторонних ресурсов.
4. При расхождении документов не откатывать реализованную функциональность по устаревшему плану. Свериться с кодом и HANDOFF, а противоречие указать в отчёте.
5. Перед правками посмотреть `git status` и текущее содержимое файлов. Не перезаписывать и не отменять чужие или уже существующие изменения.

## Координация нескольких агентов

- При параллельной работе должен быть один координатор — человек или назначенный агент. Он распределяет задачи, разрешает пересечения и определяет порядок интеграции.
- До начала задачи зафиксировать в постановке: цель, разрешённую область файлов, запрещённые области, зависимости и критерии готовности.
- Read-only исследования и аудиты можно проводить параллельно. Правки — только в непересекающихся областях либо последовательно.
- Общие файлы должен изменять один агент за раз. Это особенно важно для `prisma/schema.prisma`, миграций, `package.json`, lockfile, глобальных стилей, общих компонентов, `AGENTS.md`, `docs/HANDOFF.md` и `docs/process-log.md`.
- Не менять область задачи и не затрагивать чужие файлы без согласования. Если обнаружена необходимость более широкой правки, сначала сообщить координатору.
- Не считать контекст других агентов доступным: всё необходимое для продолжения фиксировать в коде, проектной документации и итоговом отчёте.
- Новые библиотеки, обновления зависимостей, новые разделы продукта и изменения принятых архитектурных решений — только после согласования с командой.

## Обсуждение идей между агентами

- Пространство `docs/agents/ideas/` используется для предложений и асинхронных обсуждений по продукту, архитектуре, дизайну и процессу разработки. Регламент — в `docs/agents/ideas/README.md`, шаблон — в `_TEMPLATE.md`.
- Для новой идеи создавать отдельную карточку по шаблону, предварительно проверив существующие идеи и HANDOFF. Не превращать обсуждение в изменение кода без отдельной постановки задачи.
- Отвечать на идеи новыми репликами по существу: аргументы, риски, вопросы и альтернативы. Чужие реплики не редактировать; одну карточку одновременно изменяет один участник.
- Координатор приглашает участников, передаёт им путь к карточке, обобщает позиции и выносит вопрос на решение команды. Автоматических уведомлений у пространства нет.
- Согласие агентов не считается одобрением. Реализация новых разделов, зависимостей и архитектурных изменений начинается только после явного решения команды.

## Общая среда разработки

- По умолчанию все агенты используют один рабочий каталог, одну БД на порту `5433`, одно файловое хранилище и одни каталоги сборки. Не предполагать наличие изоляции, если она специально не настроена.
- Не запускать одновременно процессы, которые меняют общее состояние: dev-сервер, сборку, `prisma generate`, миграции, сид и тесты. Такие операции выполняются последовательно и по согласованию с координатором.
- `corepack pnpm db:seed` пересоздаёт демо-данные и удаляет сессии. Запускать его только когда это нужно для задачи и другие участники предупреждены.
- Тесты используют засеянную БД и изменяют её записи. Настройка Vitest отключает параллельность только внутри одного запуска, но не между разными агентами.
- Отдельные worktree, порты, БД и каталоги загрузок можно использовать только по заранее согласованной схеме изоляции.

## Жёсткие правила проекта

- Только вымышленные данные. Никаких реальных ФИО, номеров зачёток и логинов вуза.
- Не использовать логотип реального вуза. Сохранять пометку «концепт для конкурса, не официальный сервис».
- Секреты — только в переменных окружения; не записывать их в код, Git, браузер или отчёты.
- Доступ к данным — через `src/server/repos/*` с фильтром по пользователю из сессии. Доступ по чужому ID должен возвращать 404/403; нарушения разграничения доступа проверять тестами.
- Mobile-first: проверять интерфейс на ширине 360 px и на широком экране. Результат оценивать в браузере глазами пользователя, а не только автотестами.
- Сохранять утверждённую навигацию и дизайн-систему. Не удалять существующую функциональность ради упрощения без согласования.
- Сторонние шрифты, иконки и изображения — только с разрешающей лицензией; сведения добавлять в `docs/licenses.md`.
- Push на GitHub и любые действия на VPS — только по явной команде пользователя. Платные генерации — только с согласия пользователя.
- Придерживаться стиля окружающего кода, не исправлять посторонние проблемы и не оставлять временные обходы без явного указания в отчёте.

## Продукт и дизайн: решения команды

Пересматривать только по явному решению команды (или через карточку в `docs/agents/ideas/`).

- **Простота важнее количества.** «Нужное за пару касаний»; ничего не мельтешит; функционал не теряем — второстепенное прячем за ссылками, «Показать ещё», раскрывающимися блоками. Цвет — только у важного (долг, просрочка), не у каждой строки; списки — в одну колонку сверху вниз.
- **Навигация по ролям:**
  - Студент — 4 раздела: Главная · Расписание · Учёба · Заявки; в шапке — Помощник, уведомления, профиль. Домашние задания, материалы и посещаемость — внутри «Учёбы» (`/homework`, `/courses/[id]`, `/attendance`), отдельных пунктов меню не добавлять.
  - Деканат — Заявки · Студенты · Расписание · Объявления. «Студенты» — вкладки Ведомость (с выгрузкой в Excel) · Группы · Посещаемость; по фамилии — личное дело студента.
  - Преподаватель — главная «Сегодня» (пары дня, сводка по группам); у дисциплины вкладки Журнал (со статистикой группы) · Посещаемость · Материалы · Домашние задания; по фамилии — карточка студента по дисциплине.
- **Прогноз оценки** — единые пороги для всех ролей (`src/lib/grading.ts`): доля набранного от возможного 60 % — «3»/зачёт, 75 % — «4», 90 % — «5». Цифры у деканата и преподавателя должны совпадать с «Учёбой» студента.
- **Стиль v3** (`src/app/globals.css`, `src/components/ui.tsx`): фон #FAFAFA, шрифт Onest, навигация-капсулы (активная чёрная), чёрные кнопки-пилюли, карточки 24–32 px, пастели со смыслом: мятный — справки, голубой — расписание, сиреневый — учёба, жёлтый — помощник/важное. Логотип «УНИВЕР» — только собственный (`src/components/logo.tsx`).
- **ИИ-помощник** называется просто «Помощник». Принцип: **ИИ распознаёт — человек подтверждает.** Модель готовит карточку с кнопкой (заказать справку, отметить посещаемость), выполняет действие только нажатие человека. Оценки и баллы ИИ не выставляет и не меняет (цена ошибки слишком высока); у деканата ИИ-действий нет — решения касаются других людей. Без ключа шлюза те же сценарии работают на правилах.
- **Файлы материалов и домашних заданий** — только Word, PDF, Excel, PowerPoint (`src/server/files.ts`). Демо-файлы — настоящие документы этих форматов в `prisma/fixtures/` (генератор `scripts/make-fixtures.mjs`); Markdown/текст в пользовательских файлах не использовать.
- **Демо-данные** — правдоподобные и согласованные между ролями: без одинаковых ФИО, без накладок пар у преподавателя, экзамены не в праздники; изменения сида проверять глазами в кабинетах всех ролей.

## Завершение задачи

- Выполнить проверки, соответствующие изменению. Базовая команда — `corepack pnpm check`; для тестов нужна подготовленная БД. Сборку и ручной сценарий проверять, когда они относятся к задаче.
- Не называть работу завершённой при ошибках проверок или непроверенном критичном сценарии. Точно перечислить, что проверено, а что нет и почему.
- После значимого шага добавить запись в `docs/process-log.md`: задача, инструмент/модель, ключевой промпт, результат, ошибки и исправления. При крупных изменениях обновить `docs/HANDOFF.md`. Одновременное редактирование этих документов координируется.
- Перед отчётом проверить `git status`, не удалять чужие файлы и не оставлять ненужные результаты запусков.
- Итоговый отчёт: результат, изменённые файлы, выполненные проверки, принятые решения, ограничения и нерешённые вопросы.
