Основные разрывы находятся после принятия решения: «принято» не всегда означает изменение учебных данных; загрузка замены не означает замену в открытом деле; уведомление не означает обновление открытого экрана. Поэтому наличие отдельных кнопок не подтверждает завершённость сценария.

## Разрывы, которые следует исправить

### L01 · Высокий продуктовый приоритет · Принять ДЗ и оценить ДЗ — разные, несвязанные операции

`src/server/repos/homework.ts:113`, `src/app/teacher/[groupId]/[courseId]/homework/[assignmentId]/review.tsx`, `src/server/repos/teacher.ts:79`.

В карточке сдачи есть «Принять» и «На доработку», но нет баллов. reviewSubmission меняет статус и комментарий, не создавая Grade. В журнал баллы вносятся отдельно, без submissionId/assignmentId. Студент получает уведомление вида GRADE, хотя оценка не появилась. Нельзя надёжно показать «за эту работу 15 из 20», исключить двойное выставление за неё или согласованно отозвать оценку при возврате работы.

Воспроизведено на реальной функции с подменённой БД: принятие успешно, Grade не создан.

Предложение: преподаватель сам вводит баллы в проверке, «Принять и поставить баллы» сохраняет решение и связанную оценку атомарно. Если работа без оценки — явно «Принять без баллов». При возврате ранее оценённой работы явно выбирать судьбу оценки. ИИ оценки не выставляет. Нужна согласованная модель связи оценки и работы; это продуктовая доработка, не автоматическая правка аудита.

### L02 · Высокий · Пересдача заканчивается статусом заявки, а не закрытием долга

`src/app/(student)/grades/page.tsx`, `src/server/repos/staff.ts:155`, `src/server/repos/teacher.ts`.

Студент видит долг и может запросить пересдачу. Однако в src нет операции создания/изменения Exam из решения деканата и нет записи итоговой Grade вида RETAKE/FINAL через рабочий интерфейс. Доступные операции преподавателя создают CURRENT. Даты и итоговые результаты пока приходят из сида. Переключение заявки в DONE само по себе не назначает пересдачу и не закрывает задолженность.

Предложение: «Назначить пересдачу» с дисциплиной, датой, аудиторией и ответственным; студент видит событие и уведомление; преподаватель фиксирует результат, после чего долг пересчитывается. До реализации честно указывать, что результат оформляется вне прототипа.

### L03 · Высокий · Согласованный перезачёт не отражается в успеваемости

`src/server/services/requests.ts` — decideApproval; `src/server/repos/staff.ts` — changeRequestStatus.

Преподаватель согласует, деканат завершает, но эти функции не меняют Enrollment/Grade. Нет отдельного интерфейса фиксации перезачтённого результата. Пользователь видит завершённую услугу, учебные данные остаются прежними.

Предложение: отделить согласование от исполнения; завершение допускается после явной записи результата сотрудником с журналом основания. Если учёт внешний, показывать «решение оформлено, внесение результата — вне сервиса», а не подразумевать завершение всего цикла.

### L04 · Высокий · Новая версия отклонённого документа не попадает в уже открытую заявку

`src/server/services/documents.ts` — uploadDocument/reviewDocument; `src/server/services/requests.ts` — submitRequest; `src/app/(student)/requests/[id]/page.tsx`.

При подаче создаётся RequestDocument с конкретным documentId. Деканат отклоняет его и просит новый. Повторная загрузка создаёт другую StudentDocument, но связи действующих заявок не меняются. В карточке заявки студент может дать текстовый ответ, а заменить приложенный documentId не может. После «исправления» деканат продолжает видеть старый отклонённый файл.

Предложение: действие «Заменить документ в этой заявке», которое сохраняет версии, переводит новую на проверку и возвращает дело сотруднику. Не заменять молча документы сразу во всех делах: у каждого должна сохраняться история.

### L05 · Средний · Не хватает сигналов и обновления экранов у другой роли

`src/server/repos/homework.ts` — submitHomework; `src/app/api/homework/[id]/route.ts`; `src/components/live-notice.tsx`; `src/components/teacher/shell.tsx`; `src/server/repos/staff.ts` — moveLesson/cancelLesson.

- При сдаче ДЗ не создаётся уведомление преподавателю. Счётчик работ вычисляется сервером, но открытый экран преподавателя не опрашивает эту очередь. Перезагрузка покажет работу; без неё он может не заметить сдачу.
- Студентский LiveNotice обновляет страницу только для SCHEDULE_CHANGE. После принятия ДЗ всплывающее сообщение может прийти, а старая открытая карточка останется «на проверке» до перехода/обновления.
- О переносе пары уведомляются студенты через groupUserIds; преподаватель пары в получатели не добавлен. Его расписание изменится при следующем чтении, но отдельного сигнала о переносе нет.

Это установлено чтением кода, задержки в браузере не измерялись. revalidatePath на сервере не следует считать механизмом доставки обновления в другой уже открытый браузер.

Предложение: событийная матрица «событие → получатель → уведомление → обновляемые данные»; обновление соответствующих очередей/карточек по событию или умеренному polling. Не обновлять страницу во время незавершённого ввода. Отдельно проверить два одновременно открытых кабинета.

### L06 · Средний · Запись на приём не связана с конкретным шагом жизненной ситуации

`src/server/services/situations.ts:62,83`.

getCase берёт любую запись, созданную после старта ситуации, и считает выполненным шаг «Забрать направление»/«Забрать справку». Запись на другую консультацию тоже подходит: ни caseId, ни соответствующий requestId не проверяются. Применяется appts[0] без определённой сортировки.

Воспроизведено: посторонняя запись закрыла appointment-шаг ситуации dorm.

Предложение: связывать приём с делом/заявкой/шагом, отдельно показывать «записан», «посетил» и «документ получен». Сам факт записи не подтверждает получение документа.

## Продуктовые границы, которые нужно явно обозначить

1. **Чек-лист действий или результат услуги?** NEW/NEED_INFO заявки уже засчитываются как done шага, PENDING-фото — тоже. Это соответствует текущему принципу «студент сделал своё действие», но фраза «Готово — можно завершить» выглядит как окончательный результат. Тест подтвердил PENDING → done. Показывать отдельно «Вы отправили» и «Вуз завершил»; не выдавать это за ошибку хранения данных.
2. **Перевод.** Инструмент перевода аккаунта/группы у деканата существует, но завершение APP_TRANSFER с ним не связано. Требуется явный шаг исполнения либо прозрачная ссылка на ручное действие. Не выполнять перевод только по свободному тексту заявления.
3. **Материальная помощь и общежитие.** По принятому решению деканат оформляет решение/направление, платёж и фактическое заселение выполняются вне системы. Эти границы допустимы, но DONE не должен обещать «деньги перечислены» или «заселение состоялось».
4. **Пропуски.** Уважительная причина и фактическое присутствие — разные состояния. Нужна единая подпись у всех ролей, а не замена отсутствия на присутствие. Автоматическая корректировка баллов за пропуски требует отдельного регламента.
5. **Оценки.** Для итоговых результатов, пересдач и текущих баллов нужны разные понятные действия и одинаковые расчёты во всех кабинетах. Общая функция порогов сама по себе не гарантирует одинаковую входную выборку оценок.

## Приёмочные сценарии следующего этапа

В двух независимых сессиях студента и преподавателя: выдать → увидеть → сдать → получить сигнал → вернуть с причиной → пересдать → принять с баллами → увидеть те же баллы у студента и деканата. Проверить обновление без ручной перезагрузки, повтор запроса, одновременную новую сдачу, просрочку и перевод между группами.

Для документов: подать → отклонить вложение → заменить в том же деле → проверить новый файл → завершить; старый файл остаётся в истории.

Для пересдачи/перезачёта: заявление → решение → изменение конкретного учебного результата → исчезновение долга/появление зачёта во всех кабинетах.

Для приёма: записаться из конкретной заявки → увидеть у деканата → отменить/перенести → корректно изменить план, занятость и напоминание. Эти сценарии следует проверить на отдельной согласованной БД перед утверждением «работает сквозным образом».
