## Новые находки

### F01 · P2 · Согласование перезачёта может попасть преподавателю другой подгруппы

Место: `src/server/services/requests.ts:33,43,54`.

В `teacherFor` выбирается первая пара группы по названию дисциплины и периоду. Подгруппа студента не учитывается: тип SubmitStudent даже не содержит subgroup. При разных преподавателях одной дисциплины в двух подгруппах выбор может попасть на преподавателя другой подгруппы; при нескольких преподавателях он ещё и не имеет определённого порядка. Назначенный преподаватель получает payload/комментарий заявки и право решения.

Воспроизведение: студент первой подгруппы, найденная первая пара — преподаватель другой подгруппы; submitRequest успешно создал согласование этому преподавателю. В запросе нет ни subgroup, ни OR для общих занятий. Это не позволяет студенту задать произвольного преподавателя напрямую: ошибка возникает при такой структуре расписания.

Исправление: передавать subgroup из сессии, фильтровать общие занятия или подгруппу студента; выбирать courseId, а не строковое имя. Если преподавателей несколько, задать явное правило ответственного/выбора и повторно проверить его полномочия при решении.

### F02 · P2 · Причина отсутствия раскрывается преподавателям всей группы

Место: `src/server/services/teacher.ts:10`.

`absentStudents` получает группы преподавателя, затем берёт заявления всех студентов этих групп без подгрупп. Возвращает свободный `payload.reason` на страницу преподавателя. В этом поле могут оказаться медицинские/личные подробности, хотя для учебного процесса достаточно периода и отметки «подтверждено / на рассмотрении». Ранее отсутствие прямого доступа преподавателя к личным документам не закрывает этот новый канал раскрытия текста.

Воспроизведение: функция вернула вымышленную медицинскую подробность; запрос студентов ограничен только groupId. Действительно чувствительные данные не использовались. Если команда сознательно разрешает всем преподавателям группы видеть эту информацию, нужна явная политика; из требований следует более узкая учебная связь.

Исправление: минимизировать ответ, не передавать исходную причину; учитывать подгруппу/действительную связь с конкретным студентом и необходимые занятия. Для самостоятельного предупреждения о болезни сохранять понятную границу между словами студента и решением деканата.

### F03 · P2 · Согласование не проверяет состояние основной заявки

Место: `src/server/services/requests.ts:142`.

Список скрывает часть завершённых заявок, но `decideApproval` проверяет только teacherId и PENDING у шага. Если pending-шаг остался после завершения/отклонения заявки, сервер всё ещё примет решение. В ветке REJECTED число изменённых основных заявок не проверяется: возможны событие DONE → REJECTED и уведомление об отказе при фактическом сохранении DONE. Аналогичное несоответствие возможно при конкурентном завершении заявки.

Воспроизведение: основная заявка DONE, шаг PENDING, updateMany заявки вернул count=0; функция вернула true, создала ложное событие об отказе и отправила соответствующее уведомление. Непротиворечивое состояние самого шага уже изменено.

Исправление: в общей транзакции блокировать/условно обновлять основную заявку и шаг, проверять допустимый статус заявки и count; прекращать оставшиеся шаги при конечном решении. Нужен тест конкурентного решения, а не только повторного клика по уже решённому шагу.

### F04 · P2 · Лимит двух записей на приём обходится конкурентными запросами

Место: `src/server/services/appointments.ts:51`.

`count` будущих приёмов и `create` разделены. Три запроса на разные слоты одновременно видят count=0. Уникальный slotKey защищает только конкретное время, а не квоту студента. Один аккаунт может занять больше двух слотов и мешать другим студентам; ограничитель частоты здесь отсутствует.

Воспроизведение: три параллельных вызова на разные времена успешно выполнили три create. Для проверки реальной изоляции PostgreSQL понадобится отдельный интеграционный тест.

Исправление: сериализация операций по студенту (блокировка строки) либо Serializable-транзакция с повтором конфликтов; общий серверный rate limit и горизонт бронирования. Обычная транзакция Read Committed с тем же count сама по себе гонку не устраняет.

### F05 · P2 · Ошибка напоминания маскирует успешно созданную запись

Место: `src/server/services/appointments.ts:65`.

Приём сохраняется раньше напоминания, оба действия находятся в одном try без транзакции. Если reminder.create падает, пользователь получает ошибку, хотя время уже занято. Повтор создаст другое поведение: «слот занят» либо новую запись на другое время. Нет надёжного ключа повторной операции.

Воспроизведение: create приёма успешен, create напоминания выбросил исключение; функция завершилась ошибкой, $transaction не вызывался.

Исправление: общая транзакция записи и напоминания, либо сохранение приёма с возвращением успеха и отдельная повторяемая доставка напоминания. Добавить idempotency key, чтобы сетевой повтор возвращал тот же результат.

### F06 · P2 · Будущий слот показывается свободным, но остаётся занят уникальным ключом

Места: `src/server/services/appointments.ts:29,97`, `prisma/schema.prisma` — Appointment.slotKey.

Сотрудник может отметить приём DONE/NO_SHOW за 12 часов до начала. `availability` считает занятыми только BOOKED, но markAppointment не освобождает slotKey. Поэтому будущее время показывается свободным, а реальная попытка записаться конфликтует с уникальным индексом. Отметка «не пришёл» до начала приёма также искажает статистику.

Воспроизведение: за час до слота DONE разрешён; update содержит только status; availability исключает DONE и возвращает слот free=true. Конфликт unique установлен по схеме БД, реальная вставка в БД не выполнялась.

Исправление: не разрешать финальные отметки до фактического приёма; определить единое правило доступности. Если слот намеренно освобождается, менять slotKey атомарно; если он продолжает резервироваться — availability должна считать его занятым.

### F07 · P2 · Добавленный таймаут не прекращает разбор PDF/Word

Место: `src/server/knowledge/text.ts:18`.

Promise.race прекращает ожидание вызывающей функции, но не underlying-парсер. Он продолжает потреблять память/CPU после ошибки. При блокирующей работе в event loop сам таймер тоже не гарантирует срабатывания через 20 секунд. PDF после открытия не освобождается через destroy/finally, включая ветку превышения 150 страниц. Лимит текста проверяется только после извлечения. По сравнению с первым аудитом защита улучшена, но проблема изоляции ресурсов остаётся.

Два воспроизведения: после таймаута подменённый Word-парсер продолжил работу и завершился; PDF с 151 страницей отклонён без destroy. ZIP/PDF-бомбы и уязвимости библиотек не эксплуатировались.

Исправление: отдельный процесс/worker с реальным завершением, лимиты распакованных байтов/страниц/памяти и конкурентности. clearTimeout в finally, destroy PDF во всех ветках. Ограничение в 10 МБ сжатого файла не заменяет эти меры.

### F08 · P1 для восстановления данных · Новые личные документы тоже отсутствуют в backup

Места: `src/server/services/documents.ts:24`, `deploy/backup.sh:8`.

Новый модуль хранит файлы в DATA_DIR/documents. Резервное копирование по-прежнему архивирует только uploads, пропуская и documents, и photos. В БД будут ссылки, но файлов паспортов/заявлений/фотографий после восстановления не окажется. Это расширение прежнего SEC-05; не считаем его независимой новой уязвимостью.

Исправление: согласованный backup всего необходимого DATA_DIR и БД, проверка восстановления, отдельное защищённое хранилище. Прежняя проблема `pg_dump | gzip` также не исправлена.

## Дополнительные вопросы, не выдаваемые за воспроизведённые атаки

- **Переход с отделов на один деканат.** Миграция deanery_only удаляет kind/department, но не преобразует уже существующие PENDING/WAITING согласования отделов с teacherId=null. При обновлении заполненной прежней БД такие заявки могут навсегда исчезнуть из очереди деканата, потому что deaneryQueue исключает активные согласования, а преподавателя у шага нет. Нужен интеграционный migration-тест с историческими данными и их явное преобразование. Для чистой БД без прежних заявок этот сценарий не возникает. Аналогично проверить коллизии старых многоведомственных бронирований после объединения календарей.
- **Личные документы.** Размер одного файла ограничен, суммарной квоты и rate limit загрузок нет. Добавлены более чувствительные категории файлов; нужны квота студента, журнал скачиваний сотрудников, сроки хранения и процедура удаления. PDF отдаётся inline: использовать изолированный просмотр/attachment по выбранной политике, это само по себе не доказанный XSS.
- **RAG.** Недоверенные фрагменты вставляются в system-сообщение. Не использовать их как инструкции; разделить данные и инструкции, проверять основание ответа. Вызов модели идёт до фильтра уверенности совпадения, поэтому при слабом совпадении может получиться уверенный ответ с нерелевантным источником. Это риск качества/целостности; успешная prompt-injection или утечка закрытых источников не подтверждена.
- **Проактивность и эскалации.** catch в deliverStudentDigest теперь чистит метки при обычном исключении, но аварийное завершение процесса между claim и записью чата оставит метку. `escalateOverdue` также ставит escalatedAt до успешного notify. Общая рекомендация — transactional outbox/claim с lease и повторяемая обработка. Это продолжение класса проблем доставки из первого аудита.
- **Сохранение доказательств заявки.** Удаление документа после завершения заявки каскадно удаляет RequestDocument, а удаление при одновременной подаче/изменении статуса не синхронизировано общей транзакцией. Утвердить, какие документы являются историей решения и когда допустимо их уничтожать.
- **Автовыдача.** Нужен явный список услуг, которые можно выдавать без сотрудника, а не только проверка isCertificate. Оценить жизненный цикл справок, актуальность реквизитов и отзыв после изменения данных.
