### S01. Демо-вход — небезопасное значение по умолчанию

**Код:** `src/app/login/actions.ts:44–53`, `deploy/.env.example`, `deploy/deploy.sh`.

`demoLoginAction` запрещает вход только при точном `DEMO_LOGIN === "0"`. Отсутствующая переменная, пустое значение и опечатка оставляют вход включённым. Среди разрешённых логинов есть деканат и преподаватель. В примере развёртывания стоит `DEMO_LOGIN=1`; deploy лишь печатает предупреждение. Новый сильный пароль демо-деканату не защищает этот путь: пароль здесь вообще не проверяется.

**Проверка:** при отсутствующей переменной функция создала сессию вымышленного STAFF и отправила в `/staff`; при `0` создание сессии не произошло. Это намеренная конкурсная возможность, но опасная граница между демо и настоящим сервисом. Состояние флага на VPS не проверено.

**Исправление:** включать возможность только по явному `DEMO_LOGIN=1` и только в согласованной демонстрационной среде; для настоящего запуска запретить старт/деплой с демо-входом. Демо и реальные данные держать раздельно; не переносить известные из сида учётные записи в настоящую БД. Скрытия кнопок на странице недостаточно.

### S02. Ограничение смены временного пароля существует только на странице

**Код:** `src/app/login/actions.ts:64–77`; `src/server/auth.ts:102–105`; `src/app/change-password/page.tsx:14`.

Страница перенаправляет пользователя, если `mustChangePassword=false`. Но экспортированное серверное действие этой проверки не выполняет: `userForPasswordChange()` возвращает любую активную незаблокированную сессию. Действие принимает только новый пароль и его повтор, обновляет пароль и удаляет другие сессии, сохраняя текущую. Проверка страницы не заменяет проверку самого Server Action.

**Последствие:** человек с чужой действующей сессией может закрепить захват аккаунта новым паролем и отключить остальные сессии. Знание старого пароля не требуется. Работает и для STAFF/TEACHER. Это не вход без аутентификации: сначала нужен доступ к сессии.

**Проверка:** настоящая функция с mock-пользователем STAFF, `mustChangePassword=false`, успешно записала новый хеш; текущая mock-сессия осталась исключением при удалении. БД не использовалась.

**Исправление:** в действии установки временного пароля требовать `mustChangePassword=true`; проверять условие и при записи, чтобы исключить гонку со сбросом. Для обычной смены предусмотреть отдельное действие с проверкой текущего пароля либо повторным подтверждением личности. После смены выпускать новый токен сессии; события безопасности регистрировать без паролей. Рекомендация проверки текущего пароля и повторной аутентификации описана в [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

### S03. Граница подгруппы не применяется к журналу и текущим оценкам

**Код:** `src/server/repos/teacher.ts:34–35,39–57,79–99,134–140`; дополнительная поверхность — `src/server/files.ts:185–188`.

`teachesPair` отвечает только на вопрос, есть ли у преподавателя актуальная пара для сочетания «группа + дисциплина». `addGrade` проверяет текущий семестр и эту пару, но не запрашивает подгруппу студента. `deleteGrade` и массовое выставление используют аналогичную границу; журнал выбирает всех студентов группы. Само наличие поля subgroup в отображаемых строках не ограничивает доступ.

**Последствие:** преподаватель только первой подгруппы может получать журнал и менять CURRENT-баллы студента второй подгруппы. В выдаче вложений преподавателю действует та же проверка группы/дисциплины — следует включить её в исправление. Доступ к личным паспортным документам этим путём не подтверждён: для них действует отдельный запрет преподавателю.

**Проверка:** реальный `addGrade` создал mock-оценку студенту другой подгруппы; перехваченный запрос проверки пары не содержал subgroup. Проверка старого семестра уже исправлена и теперь присутствует.

**Исправление:** единая проверка актуальной учебной связи с конкретным студентом: совпадение подгруппы либо занятие для всей группы (`subgroup=null`), период и дисциплина. Использовать её при чтении журнала, индивидуальной и массовой записи/удалении, доступе к сдачам и файлам. В согласовании заявок такой принцип уже применяется (`src/server/services/requests.ts:45–68`). Если доступ ко всей группе педагогически необходим, оформить отдельное полномочие, а не получать его автоматически через любую подгруппу.

### S04. Резервная копия не завершается без каталога фотографий

**Код:** `deploy/backup.sh:6,16,19–24`; исходное создание тома — `Dockerfile:33`.

Внутри `dirs="$(docker compose exec ... sh -c '... for d in uploads documents photos; do [ -d "$d" ] && printf ...; done')"` код возврата цикла равен коду последней итерации. Если `photos` ещё не существует, `[ -d photos ]` возвращает 1. `docker compose exec` передаёт ошибку наружу, присваивание возвращает 1, а `set -e` завершает backup до файлового архива. Dockerfile заранее создаёт только uploads; отсутствие photos в новом томе нормально.

**Проверка:** точный shell-фрагмент выполнен в отдельной временной папке только с uploads: stdout `uploads `, exit=1. Родитель с `set -euo pipefail` не достиг следующей команды. Docker и рабочие файлы не использовались.

**Последствие:** уже опубликован `${day}.sql.gz`, но файловой части нет — загрузки и документы из этой копии не восстановить. Проверять только наличие SQL-архива недостаточно.

**Исправление:** корректно завершать обнаружение отсутствующих необязательных каталогов успешным кодом; проверять комплект БД + файлы целиком и публиковать маркер готовности только после обеих частей. Ошибки должны доходить ответственному сотруднику.

**Отдельный остаточный риск:** `pg_dump` и tar не создают общий снимок. Например, после снимка БД студент заменяет ДЗ, прежний файл удаляется (`src/server/repos/homework.ts:252–256`), а tar уже не включает его. Восстановленная БД будет ссылаться на отсутствующий файл. Нужны согласованный снимок/короткая блокировка изменений либо версионируемое хранилище с задержкой удаления и проверкой ссылок при восстановлении. Этот временной сценарий установлен по последовательности операций, полный restore не выполнялся.

### S05. Чтение БД раскрывает пригодные для входа токены сессий

**Код:** `src/server/auth.ts:63–75,90–97`, `prisma/schema.prisma:126–135`.

Случайный 256-битный идентификатор одновременно записывается в cookie sid и в Session.id. Это хороший уровень случайности, но содержимое таблицы уже является готовыми ключами доступа. При утечке свежего дампа атакующему не нужно взламывать Argon2, чтобы войти в ещё действующие сессии. Срок — до 30 дней; блокировка/удаление сессии прекращает доступ раньше. S02 дополнительно позволяет закрепить доступ сменой пароля.

**Проверка:** в настоящем `createSession` перехвачены аргументы БД и cookies: значения равны. Сам токен не печатался.

**Исправление:** в cookie оставлять случайный токен, в БД хранить его SHA-256 или HMAC-отпечаток и искать по нему. Для случайного 256-битного токена медленный Argon2 не требуется. При переходе отозвать старые сессии; после инцидента отозвать все сессии отдельно от смены пользовательских паролей. Сократить срок и добавить idle-timeout для привилегированных ролей.

### S06. Квота документов проверяется отдельно от сохранения

**Код:** `src/server/services/documents.ts:59–87`.

`aggregate` проверяет 30 файлов / 100 МиБ, затем выполняются обработка, запись файла и создание строки. Между чтением квоты и созданием нет блокировки/атомарного резервирования. Несколько запросов видят одинаковый остаток.

**Проверка:** при исходных 29 файлах и 90 МиБ две параллельные загрузки по 6 МиБ прошли проверки: получились 31 файл и 102 МиБ. Диск и БД подменены mock-реализациями; реальных загрузок не было.

**Последствие:** лимиты не гарантируют защиту от заполнения диска. Для обычных материалов/вложений `storeFiles` ограничивает один запрос, но не общий объём пользователя/вуза. Полного заполнения диска не воспроизводил.

**Исправление:** атомарное резервирование квоты на студента с компенсацией при ошибке, либо блокировка в транзакции и согласованное подтверждение записи. Добавить общую квоту/свободный резерв хранилища, лимиты параллельных загрузок, мониторинг места и очистку неподтверждённых файлов. Изолировать данные приложения от диска ОС/БД, чтобы заполнение загрузок не останавливало всё развёртывание.

### S07. Runtime использует административную роль PostgreSQL

**Код:** `deploy/docker-compose.yml:10,25`.

`POSTGRES_USER=univer` задаёт начального суперпользователя официального образа; приложение использует тот же логин и пароль в DATABASE_URL. Это подтверждается [документацией postgres Docker Official Image](https://hub.docker.com/_/postgres). Для уже существующего тома переменная не меняет права: фактические роли VPS не проверены.

**Последствие:** при компрометации приложения/его DB-учётных данных возможности атакующего существенно шире требуемых CRUD-операций: вся БД, административные операции и средства PostgreSQL, доступные суперпользователю. Наличие SQL-инъекции или удалённого выполнения кода этим аудитом не доказано.

**Исправление:** отдельная runtime-роль без SUPERUSER/CREATEROLE/CREATEDB и без прав миграций; отдельный закрытый migration/backup-процесс с необходимыми полномочиями. Само отсутствие опубликованного наружу порта БД полезно, но не ограничивает действия уже захваченного app-контейнера.

## Что уже защищено и перепроверено

- Пароли хешируются `@node-rs/argon2`: фактический результат — **Argon2id, m=19456 KiB, t=2, p=1**, разные соли для одинакового пароля. Это соответствует минимальной конфигурации [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). «Ещё раз захешировать» пароли не нужно; исходный пароль по такому хешу расшифровать нельзя, но слабый пароль всё ещё можно пытаться подобрать.
- Сессии имеют случайные токены; cookie HttpOnly и SameSite=Lax. Secure включается при APP_URL с https — перед настоящим запуском нужна проверка обязательного HTTPS и корректной конфигурации, чтобы флаг не зависел от незаметной опечатки.
- Центральная проверка закрывает доступ заблокированному пользователю и кабинету с временным паролем. Сброс пароля и блокировка удаляют сессии; пароли не записываются в AccountEvent.
- Личные документы проверяются по владельцу/области деканата; преподавателю не выдаются. Вложения скачиваются с проверкой прав, attachment/nosniff и private/no-store. Ключи файлов случайные, read-функции запрещают пути произвольного вида. Это проверка указанных веток исходников, не полный набор отрицательных HTTP-тестов.
- Push-endpoint ограничен HTTPS и известными доменами браузерных push-сервисов; прежний произвольный SSRF-адрес больше не допускается в проверенном коде.
- Фото перекодируются с ограничением пикселей и удалением EXIF. Библиотека ограничивает страницы/текст и сериализует извлечение; у PDF при извлечении есть destroy по таймауту.
- В backup теперь включены uploads, documents и photos, есть pipefail, временные файлы, проверки архивов и umask 077. Прежнюю проблему «копируется только uploads» не считаю оставшейся; S04 — другой дефект в новом обнаружении каталогов.
- Caddy ограничивает тело запроса 13 MB и включает HSTS, Next задаёт nosniff/защиту от фреймов и другие заголовки. CSRF для мутирующих API проверяется по Origin/Host. Это не проверка конфигурации прокси на VPS.
- В GigaChat не обнаружено отключения TLS-проверки: доверенный CA добавляется к корневым сертификатам. Ключи используются на сервере, в проверенных ветках не включаются в ответ клиенту. Реальные ключи и запросы к провайдеру не проверялись.

## Дополнительные меры перед персональными данными

Это архитектурные риски и предложения, а не дополнительно доказанные взломы.

1. **Шифрование документов и резервных копий.** `documents.ts`/`photos.ts` пишут исходные данные файлов, backup использует gzip/tar без шифрования. Отсутствие шифрования самого VPS по исходникам установить нельзя. Пароли нужно хешировать; паспорта, справки, фотографии и сообщения, которые требуется читать обратно, — при необходимости шифровать. Практический минимум: шифрованная копия вне VPS, ключ отдельно от backup, ограниченный доступ и проверенное восстановление. Для наиболее чувствительных файлов рассмотреть прикладное AEAD-шифрование с управлением ключами. Оно помогает при краже тома/backup, но не скрывает данные от работающего приложения, уже захваченного атакующим.
2. **Данные в ИИ.** При включённом провайдере `assistant.ts:50–52` отправляет контекст и историю: `context.ts` содержит имя, фамилию, группу, успеваемость, посещаемость, расписание. У преподавателя в `teacher.ts:320–330` в промпте перечисляются ФИО и userId студентов. Это реальный поток данных по коду, а не доказанная несанкционированная передача: фактическое включение модели и условия провайдера не проверены. До реальных данных определить допустимый состав, убрать лишние идентификаторы, псевдонимизировать, не отправлять документы/медицинские причины, задать сроки хранения и правила доступа у выбранного провайдера. В демонстрации использовать только вымышленные данные, как требуют правила проекта.
3. **Изоляция парсеров и карантин вложений.** У Word `withTimeout(mammoth.extractRawText(...))` прекращает ожидание, но не отменяет разбор; MAX_TEXT применяется после извлечения. Очередь не имеет предельной длины и удерживает ожидающие буферы. Нужны отдельный процесс с реальным прекращением работы, CPU/RAM/time/decompressed-size limits и ограниченная очередь. Для выдачи пользовательских документов — антивирусный карантин и понятная политика активного содержимого. Проверка сигнатур/запрет VBA не равны антивирусу. Произвольное выполнение кода через файл не подтверждено.
4. **Доступ персонала.** MFA/SSO для деканата и преподавателей; повторное подтверждение для сброса чужих паролей и чувствительных массовых действий. Персональные аккаунты вместо общего `dekanat`. Раздельные права на документы, аккаунты и учебные результаты; журнал скачивания чувствительных файлов и изменений оценок без лишних персональных данных в логах.
5. **Защита от перебора/DoS.** Лимиты входа и сообщений находятся в памяти одного процесса, исчезают после перезапуска и не объединяются между репликами. Для входа есть счётчики login+IP и IP, но нет общей границы попыток на аккаунт с разных адресов. Нужны согласованные ограничения, мониторинг аномалий, очистка старых ключей и ограничение количества одновременных дорогостоящих операций. Не заменять это постоянной блокировкой аккаунта, которую может вызвать посторонний.
6. **Контейнеры и поставка.** Runtime уже работает не от root. Дополнить лимитами ресурсов, урезанием capabilities/no-new-privileges, минимальным составом runtime, проверкой образов и SBOM. В `.dockerignore` добавить data/backups/audit-артефакты: сейчас `COPY . .` на этапе сборки может унести их в build context/cache; автоматическое попадание всех этих файлов в финальный runtime-образ не утверждается. Миграции завершать до допуска трафика, обеспечить healthcheck и план отката без потери данных.
7. **CSP, хранение и восстановление.** CSP сначала внедрить в Report-Only с учётом Next и inline-скрипта темы. Задать RPO/RTO и провести восстановление БД вместе с файлами на отдельном стенде; наличие backup.sh не доказывает работу cron, вынесенных копий и восстановления.
