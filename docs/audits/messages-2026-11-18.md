# Аудит сообщений, прав доступа и вложений — 18.11.2026

Режим: только статическое чтение кода и документов. Тесты, БД, сборка, сервер и браузер не запускались. Правила сверены с `AGENTS.md` и `docs/agents/ideas/I-20261118-soobshcheniya.md`, включая учтённые замечания по факультетской области, актуальным преподавателям, вложениям и push без текста.

## Краткий итог

Найдено **13 находок: 7 средних и 6 низких**. Высоких находок нет.

Базовая модель личных диалогов реализована правильно: студент ↔ студент запрещён, связь студента и преподавателя проверяется по занятиям за последние 150 дней, чужой DIRECT не открывается по подменённому `id`, а вложения сообщений имеют отдельную проверку видимости. Основные проблемы — маршрутизация преподаватель ↔ деканат, неограниченный выбор преподавателя сотрудником факультета, слабая привязка повода к адресату, повторная отправка и согласованность файлов с уже сохранённым сообщением.

## Находки

### 1. Переписка преподавателя с деканатом не попадает к сотруднику факультета; инициатор может потерять доступ к своей новой теме

- **Серьёзность:** средняя.
- **Почему это проблема:** при старте преподаватель → деканат и сотрудник → преподаватель записывается `facultyId = null`. Сотрудник с конкретным `facultyId` видит только обращения своего факультета и не получает такие записи ни в списке, ни в push. Если сотрудник факультета сам пишет преподавателю, после создания он перенаправляется на `/staff/messages/[id]`, но `visibleWhere` уже не пропускает его собственный диалог: пользователь получает 404. Ответ преподавателя также останется невидимым для инициатора. В демо это скрыто тем, что основной сотрудник — общий деканат с `facultyId: null` и видит всё.
- **Место:** `src/server/repos/messages.ts:35-41`, `src/server/repos/messages.ts:248-252`, `src/server/repos/messages.ts:263-267`, `src/server/repos/messages.ts:335-343`, `prisma/seed.ts:378-379`, `prisma/seed-messages.ts:81-93`.
- **Предложение по исправлению:** определить явную маршрутизацию для преподавателя: факультет выбранной дисциплины/группы, отдельное назначение на факультет либо осознанный общий деканат. Не оставлять `null` случайно. Если общее обращение разрешено, область видимости и получатели push должны явно включать инициатора без открытия остальных DIRECT. Добавить тесты с реальным сотрудником ограниченного факультета для обоих направлений и для открытия только что созданной темы.

### 2. Сотрудник факультета может выбрать любого преподавателя, включая преподавателя только другого факультета

- **Серьёзность:** средняя.
- **Почему это проблема:** карточка разрешает деканату писать студентам и преподавателям в пределах своего факультета. Список адресатов сотрудника включает всех преподавателей с `userId`, а сервер ограничивает факультет только для студента-адресата. Для преподавателя проверки нет. Сотрудник Факультета А может отправить сообщение преподавателю, у которого занятия только у Факультета Б; из-за находки 1 он сделает это вслепую, но само запрещённое действие будет сохранено.
- **Место:** `src/server/repos/messages.ts:210-215`, `src/server/repos/messages.ts:253-269`, правило — `docs/agents/ideas/I-20261118-soobshcheniya.md:23`.
- **Предложение по исправлению:** ввести явную связь преподавателя с факультетом/назначением либо вычислять её по актуальным занятиям. Применять одинаковый предикат и в `recipients`, и в `startConversation`; фильтрация только интерфейсного списка недостаточна. Проверить адресата, который имеет занятия только в чужом факультете.

### 3. Повод проверяется только для отправителя и не связывается с адресатом; для деканата часть поводов вообще вне факультетской области

- **Серьёзность:** средняя.
- **Почему это проблема:** `resolveContext` подтверждает доступ отправителя, но `startConversation` не использует `teacherUserIds` и не проверяет пару «адресат + повод». Преподаватель, работающий с группами А и Б, может начать разрешённый диалог со студентом Б и подставить своё задание группы А. Студент увидит название задания, но ссылка `/homework/[id]` приведёт его на 404. Аналогично студент может выбрать одного преподавателя, а повод — задание другого. Для `STAFF` ветки `ASSIGNMENT` и `COURSE` не ограничивают выборку факультетом, поэтому сотрудник может получить название сущности другого факультета и создать вводящий в заблуждение контекст.
- **Место:** `src/server/repos/messages.ts:143-171`, `src/server/repos/messages.ts:174-186`, `src/server/repos/messages.ts:273-278`, `src/components/messages/views.tsx:168-188` (`teacherUserIds` влияет только на интерфейсный фильтр).
- **Предложение по исправлению:** проверять всю тройку «отправитель — адресат — повод» на сервере. Для задания учитывать его группу и преподавателя, для дисциплины — актуальное преподавание, для заявки — студента и факультет. В ветках сотрудника добавлять `group.program.facultyId`/связанного студента в `where`. Не показывать ссылку адресату, если соответствующий объект ему недоступен.

### 4. Ошибка post-commit обработки может оставить сообщение в БД, удалить его файлы и вернуть пользователю 500

- **Серьёзность:** средняя.
- **Почему это проблема:** при создании диалога `pushRecipients` находится внутри того же `try/catch`, что и `conversation.create`. Если после успешного коммита один из запросов БД в `pushRecipients` завершится ошибкой, `catch` удалит физические файлы, хотя строки сообщения и вложений уже сохранены: участники видят вложения, но скачивание возвращает 404. Повторная попытка пользователя создаёт второй диалог. При ответе `pushRecipients` вызывается после `try`, поэтому аналогичная ошибка возвращает 500 при уже созданном сообщении и провоцирует дубль. Сбои самого web-push перехватываются отдельно и к этому сценарию не относятся.
- **Место:** `src/server/repos/messages.ts:280-300`, `src/server/repos/messages.ts:310-323`, `src/server/repos/messages.ts:335-350`, `src/app/api/files/[id]/route.ts:13-14`.
- **Предложение по исправлению:** после успешного коммита никогда не удалять файлы из-за ошибки уведомления. Выполнять доставку push отдельной best-effort операцией с `catch`/логированием и не превращать её сбой в ошибку сохранённого сообщения. Для строгой гарантии использовать транзакционную outbox-запись и фоновую доставку; идемпотентность клиентского запроса нужна независимо.

### 5. Нет защиты от повторной отправки; Ctrl+Enter обходит блокировку кнопки

- **Серьёзность:** средняя.
- **Почему это проблема:** повторный POST создаёт ещё одно сообщение и новый push, а повторное создание диалога — отдельную тему. В `ReplyForm.send` нет проверки `pending`: неактивная кнопка не мешает повторно вызвать `send` через Ctrl/⌘+Enter или повторный submit. Быстрые повторы, два окна или повтор после неоднозначной ошибки приводят к дублям. Ограничение 40 сообщений за 10 минут не предотвращает несколько одинаковых отправок подряд.
- **Место:** `src/components/messages/client.tsx:28-42`, `src/components/messages/client.tsx:65-78`, `src/components/messages/client.tsx:128-149`, `src/server/repos/messages.ts:280-296`, `src/server/repos/messages.ts:303-323`.
- **Предложение по исправлению:** немедленно блокировать повторный `send` и проверять `pending` в начале функции. Добавить генерируемый на клиенте request/idempotency key и уникальное ограничение в БД; повтор того же ключа должен возвращать уже созданный результат без сообщения и push. Добавить тесты двух одинаковых запросов и повторной доставки после ошибки ответа.

### 6. Частичная запись файлов и каскадные удаления оставляют сироты на диске

- **Серьёзность:** средняя.
- **Почему это проблема:** `storeFiles` вызывается до `try` в обоих методах отправки. Если второй файл записался с ошибкой, первый уже находится на диске, но `catch`, который удаляет `stored`, ещё не будет выполнен. `removeStored` игнорирует все ошибки `unlink`. Каскадное удаление Conversation/Message/Attachment очищает только БД; например, очистка созданных диалогов в `afterAll` теста не удаляет загруженные тестом файлы. Аналогичная проблема остаётся при любом будущем удалении переписки.
- **Место:** `src/server/files.ts:48-60`, `src/server/files.ts:68-70`, `src/server/repos/messages.ts:280`, `src/server/repos/messages.ts:310`, `prisma/schema.prisma:519-520`, `prisma/schema.prisma:560-582`, `tests/messages.test.ts:23-26`.
- **Предложение по исправлению:** откатывать уже записанные ключи внутри самого `storeFiles` при любой ошибке; ошибки удаления логировать и добавить периодическую сверку файлов с БД. В тестовой очистке сначала читать `storageKey` вложений, затем удалять их с диска и только после этого удалять диалоги.

### 7. Вложения сообщений по-прежнему проверяются только по расширению

- **Серьёзность:** средняя.
- **Почему это проблема:** произвольное содержимое можно отправить как `document.pdf` или `macro.doc`; MIME также назначается по расширению. Ограничения 10 МБ/5 файлов/25 МБ работают, но не подтверждают тип документа. Скачивание как attachment и `nosniff` снижает риск исполнения в браузере, однако вредоносный документ всё равно может быть доставлен другому пользователю от имени доверенного кабинета.
- **Место:** `src/server/files.ts:18-27`, `src/server/files.ts:33-45`, `src/server/files.ts:54-59`.
- **Предложение по исправлению:** проверять сигнатуры PDF/OLE2 и ZIP-структуру OOXML с обязательными элементами пакета, при необходимости добавить антивирусное сканирование. Тест должен отправить HTML или исполняемый файл с разрешённым расширением и получить отказ.

### 8. Новое сообщение не создаёт запись в общем колокольчике уведомлений

- **Серьёзность:** низкая.
- **Почему это проблема:** карточка обещает «уведомлением + push». Сейчас отправляется только web-push и обновляется отдельный счётчик значка «Сообщения». В таблице `Notification` запись не появляется, поэтому пользователь без разрешения на push не увидит сообщение в колокольчике и общем списке уведомлений. Это не утечка и не повторная отправка, но расхождение с заявленным сценарием.
- **Место:** `src/server/repos/messages.ts:15`, `src/server/repos/messages.ts:334-350`, `src/server/notify.ts:7-15`, `src/components/messages/messages-link.tsx:8-24`, ожидание — `docs/agents/ideas/I-20261118-soobshcheniya.md:31`.
- **Предложение по исправлению:** либо явно закрепить, что значок сообщений заменяет колокольчик, либо создавать `Notification` с нейтральным текстом и ссылкой на диалог. Ключ дедупликации должен включать `messageId`, чтобы одно сообщение создавало ровно одно уведомление на получателя.

### 9. Счётчики и поиск учитывают только 200 последних диалогов

- **Серьёзность:** низкая.
- **Почему это проблема:** `listConversations` сначала ограничивает выборку 200 записями и только затем в JS применяет поиск и фильтр `awaiting`. `unreadConversations` считает по этому же списку. Если старое непрочитанное или ожидающее ответа обращение оказалось за пределами 200 последних, оно исчезает из счётчика и результатов поиска. Кроме того, значок каждые 10 секунд загружает участников и последние сообщения до 200 диалогов вместо лёгкого count-запроса.
- **Место:** `src/server/repos/messages.ts:93-108`, `src/server/repos/messages.ts:111-115`, `src/components/messages/messages-link.tsx:8-14`.
- **Предложение по исправлению:** перенести поиск и условия статусов в БД, считать непрочитанные отдельным запросом без `take: 200`, добавить курсорную пагинацию списка. Для деканата отделить count ожидающих ответа от count непрочитанных, сохранив текущую командную семантику «новых».

### 10. Открытие диалога может пометить прочитанным сообщение, которого пользователь ещё не видел

- **Серьёзность:** низкая.
- **Почему это проблема:** `openConversation` сначала читает сообщения, затем записывает `lastReadAt = new Date()`. Если новое сообщение вставлено между этими операциями, отметка времени окажется позже него, хотя в возвращённом наборе его нет. Счётчик сбросится, а пользователь увидит сообщение только после следующего обновления страницы.
- **Место:** `src/server/repos/messages.ts:119-135`.
- **Предложение по исправлению:** выставлять `lastReadAt` по `createdAt` последнего сообщения из фактически возвращённого набора, а не по текущему времени сервера. При необходимости объединить чтение последнего `createdAt` и обновление отметки в транзакцию с подходящей изоляцией.

### 11. Длинный ответ молча обрезается, а новое сообщение с теми же данными отклоняется с общей ошибкой

- **Серьёзность:** низкая.
- **Почему это проблема:** API ответа сначала обрезает текст до 5000 символов, после чего `cleanBody` молча укорачивает его до 4000. Пользователь API может потерять конец сообщения, не получив предупреждения. При создании диалога схема вместо этого отклоняет текст свыше 4000 с общим «Проверьте поля сообщения». Поведение двух форм различается, хотя визуально обе имеют `maxLength=4000`.
- **Место:** `src/server/repos/messages.ts:28`, `src/server/repos/messages.ts:231`, `src/app/api/messages/[id]/route.ts:19`, `src/app/api/messages/route.ts:9-15`, `src/app/api/messages/route.ts:30`.
- **Предложение по исправлению:** использовать одинаковую проверку во всех методах: не обрезать содержимое, а возвращать конкретную ошибку «Сообщение не должно превышать 4000 символов». Тему также валидировать без молчаливого усечения.

### 12. Ограничение частоты действует только внутри одного процесса

- **Серьёзность:** низкая.
- **Почему это проблема:** счётчик 40 сообщений за 10 минут хранится в `Map` памяти процесса. Он сбрасывается при перезапуске и не синхронизируется между репликами приложения. При горизонтальном масштабировании пользователь может превысить лимит, а при рестарте защита исчезает. Дополнительно при создании диалога лимит срабатывает до проверки адресата и повода, поэтому ошибочные попытки расходуют квоту.
- **Место:** `src/server/repos/messages.ts:222-229`, `src/server/repos/messages.ts:238-243`, `src/server/repos/messages.ts:303-310`.
- **Предложение по исправлению:** для прототипа явно зафиксировать ограничение одного процесса; для нескольких реплик использовать общее хранилище счётчиков или записи БД с окном времени. Проверки адресата выполнять до учёта квоты, а сами повторы блокировать idempotency key независимо от rate limit.

### 13. При полностью пустом списке адресатов форма не объясняет доступный выход

- **Серьёзность:** низкая.
- **Почему это проблема:** если `recipients` вернул пустой массив, интерфейс показывает только «Никого не нашлось». Кнопка отправки остаётся доступной, но при нажатии появляется «Выберите, кому написать», хотя выбрать некого. Для студента без доступного преподавателя этой тупиковой ситуации нет: деканат остаётся в списке; для преподавателя деканат также есть. Проблема относится к общему крайнему случаю, прежде всего сотрудника с пустой областью.
- **Место:** `src/server/repos/messages.ts:194-217`, `src/components/messages/client.tsx:112-125`, `src/components/messages/client.tsx:130-133`, `src/components/messages/client.tsx:173-183`.
- **Предложение по исправлению:** при нулевом списке показывать отдельное пустое состояние с причиной и ссылкой назад/в деканат, скрывать поля и блокировать отправку. Для отсутствующих преподавателей у студента сохранить текущий понятный маршрут в деканат.

## Что проверено и выглядит надёжным

- **Студент ↔ студент запрещено сервером:** ветки `startConversation` допускают только разрешённые пары ролей; простое скрытие адресата в UI не является единственной защитой (`src/server/repos/messages.ts:253-269`).
- **Личный диалог требует актуальной учебной связи:** студент → преподаватель и преподаватель → студент проверяют занятия в группе за последние 150 дней как при получении адресатов, так и при отправке (`src/server/repos/messages.ts:30-31`, `src/server/repos/messages.ts:194-208`, `src/server/repos/messages.ts:255-262`).
- **Подмена id личного диалога не открывает его:** для студента/преподавателя `visibleWhere` требует участия; деканат ограничен DEANERY своего факультета или общей областью (`src/server/repos/messages.ts:35-41`, `src/server/repos/messages.ts:120-128`).
- **Вложения используют отдельную ветку message:** доступ повторяет видимость диалога, сотрудник не получает доступ к DIRECT, а прежние правила для файлов сдач не расширены (`src/server/files.ts:75-107`). Это учитывает замечание из обсуждения идеи.
- **Заявка как повод ограничена корректно:** студент — только своя заявка, сотрудник — заявка студента своего факультета; чужой REQUEST отклоняется (`src/server/repos/messages.ts:144-150`). Остальные виды поводов требуют усилений из находки 3.
- **Непрочитанные в обычном объёме вычисляются понятно:** для личного диалога используется `lastReadAt`, собственное последнее сообщение не считается новым; для деканата ожидание определяется последним сообщением не от сотрудника (`src/server/repos/messages.ts:82-89`, `src/server/repos/messages.ts:99-108`). Ограничения описаны в находках 9–10.
- **Ответ не от сотрудника открывает решённое обращение повторно:** смена статуса, создание сообщения и отметка прочтения выполняются одной транзакцией; установить статус может только сотрудник в своей области (`src/server/repos/messages.ts:303-331`).
- **Push не раскрывает текст и имена файлов:** передаются только «Новое сообщение» и имя отправителя/«Деканат», ссылка ведёт в кабинет соответствующей роли; личный получатель исключает отправителя (`src/server/repos/messages.ts:334-350`). Маршрутизация teacher ↔ deanery — исключение, описанное в находке 1.
- **Пустые сообщения и базовые лимиты обрабатываются:** HTTP отфильтровывает пустые файлы, репозиторий отклоняет сообщение без текста и файлов, тема обязательна; файлы ограничены 10 МБ, пятью штуками и 25 МБ суммарно (`src/app/api/messages/route.ts:31-34`, `src/app/api/messages/[id]/route.ts:17-19`, `src/server/repos/messages.ts:238-242`, `src/server/files.ts:41-60`).
- **Основные ошибки понятны:** «Можно писать только преподавателям своих дисциплин», «Диалог не найден», «Повод для сообщения не найден», «Напишите сообщение» возвращаются в форму; чужой диалог при ответе становится 404 (`src/server/repos/messages.ts:253-276`, `src/app/api/messages/[id]/route.ts:21-24`, `src/components/messages/client.tsx:35-41`).
- **Демо-данные разнообразны:** есть DIRECT, новые и решённые обращения, переписка преподавателя с деканатом и исходящее сообщение деканата студенту с разными отметками прочтения (`prisma/seed-messages.ts:35-107`). Общий сотрудник в демо объясняет, почему факультетская ошибка маршрутизации не проявляется на основном аккаунте.

## Что нельзя проверить без запуска и почему

- **Реальные HTTP-сценарии и 404 после создания:** статически видна причина, но полный путь через Route Handler, redirect и рендер страницы требует запросов к приложению.
- **Параллельные отправки и гонки прочтения:** фактический порядок транзакций, уникальность idempotency key и состояние счётчика проверяются конкурентными тестами.
- **Ошибки БД после коммита и сбои диска:** потеря файлов, частичная запись и очистка сирот требуют управляемого отказа инфраструктуры.
- **Push:** реальные получатели, число доставок на устройства, замена по `tag`, ошибки провайдера и поведение без VAPID проверяются в тестовом окружении.
- **Rate limit:** перезапуск процесса и несколько реплик невозможно смоделировать чтением.
- **Интерфейс:** видимость ошибок, повторный Ctrl+Enter, пустые состояния, ссылки на недоступный повод и мобильное поведение требуют браузера.
