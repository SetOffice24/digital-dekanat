# Аудит домашних заданий, материалов и файлов — 18.11.2026

Режим: только статическое чтение кода и документов. Тесты, БД, сборка, сервер и браузер не запускались. Выводы о правах и последовательности операций подтверждены по коду; фактическое поведение инфраструктуры при сбоях и параллельных запросах требует отдельных проверок.

## Краткий итог

Найдено **10 находок: 6 средних и 4 низкие**. Высоких находок нет.

Основные границы доступа реализованы правильно: студент получает задания только своей группы и только свою сдачу, преподаватель проверяется по паре «группа + дисциплина», деканат не может скачать студенческий файл через существующий маршрут. Главные риски — гонки между сдачей и проверкой, отсутствие версии сдачи, неатомарность БД и диска, проверка содержимого только по расширению и неидемпотентные уведомления.

## Находки

### 1. Повторная сдача может перезаписать уже принятое решение преподавателя

- **Серьёзность:** средняя.
- **Почему это проблема:** студент начал повторную сдачу, когда его работа была `SUBMITTED`; `submitHomework` прочитал это состояние и прошёл проверку. В этот момент преподаватель поставил `ACCEPTED`. После этого студенческий `upsert` снова записывает `SUBMITTED`, очищает `reviewedAt` и `teacherComment`. В результате принятое решение теряется, хотя комментарий в коде обещает «Принятое — не меняется».
- **Место:** `src/server/repos/homework.ts:145-156` (проверка `ACCEPTED` вне транзакции и безусловный `update`), `src/server/repos/homework.ts:86-99` (независимая проверка преподавателем).
- **Предложение по исправлению:** добавить версию сдачи или оптимистическую блокировку. Обновление студента должно выполняться с условием по ожидаемой версии и `status != ACCEPTED` внутри транзакции; при несовпадении возвращать конфликт, а не перезаписывать решение. Аналогичное условие нужно для проверки преподавателя. Добавить конкурентный тест «принятие параллельно с повторной сдачей».

### 2. Проверка преподавателя не привязана к версии сдачи

- **Серьёзность:** средняя.
- **Почему это проблема:** преподаватель открыл файлы версии 1. Студент затем отправил версию 2, но запись `Submission` и её `id` остались прежними. Со старой страницы преподаватель нажимает «Принять», и `reviewAction` передаёт только `submissionId`: принятой оказывается версия 2, которую преподаватель не видел. Даже без одновременных запросов здесь возможна проверка не того содержимого.
- **Место:** `src/app/teacher/[groupId]/[courseId]/homework/[assignmentId]/actions.ts:8-16`, `src/app/teacher/[groupId]/[courseId]/homework/[assignmentId]/review.tsx:12-20`, `src/server/repos/homework.ts:86-99`, `src/server/repos/homework.ts:151-155`.
- **Предложение по исправлению:** передавать в действие ожидаемые `submittedAt` или монотонную `version`, отображённые преподавателю вместе с файлами. В БД менять статус только при совпадении версии; при изменении сдачи показывать «Студент отправил новую версию — откройте её перед проверкой». Для надёжного аудита версий рассмотреть отдельные записи попыток вместо перезаписи одной `Submission`.

### 3. Две одновременные сдачи приводят к гонке и могут оставить файлы-сироты

- **Серьёзность:** средняя.
- **Почему это проблема:** при первой сдаче два запроса могут одновременно получить `prev = null`, сохранить разные файлы и выполнить `upsert` по одному уникальному ключу. Один запрос может получить ошибку уникальности либо последняя операция перезапишет результат предыдущей. При повторной сдаче оба запроса читают один список прежних файлов и независимо заменяют вложения; проигравшие новые файлы остаются на диске без записей в БД. Блокировка кнопки в браузере от отдельных HTTP-запросов не защищает.
- **Место:** `src/server/repos/homework.ts:145-157`, `prisma/schema.prisma:484-499` (уникальность только `[assignmentId, studentId]`, версии нет), `src/server/files.ts:48-60` (файлы сохраняются до транзакции).
- **Предложение по исправлению:** использовать версию/условное обновление и обрабатывать конфликт как 409; для первой сдачи перехватывать конфликт уникальности и не превращать его в 500. Добавить idempotency key для повторной доставки того же запроса. Ключи файлов проигравшей операции удалять, а сценарии «два первых запроса» и «две повторные сдачи» проверять конкурентными тестами.

### 4. Жизненный цикл файлов на диске не согласован с транзакциями БД

- **Серьёзность:** средняя.
- **Почему это проблема:** файловая система не участвует в транзакции Prisma. Если запись второго файла на диск завершилась ошибкой, первый уже сохранённый файл останется. Если после `storeFiles` упадёт создание материала/задания или транзакция сдачи, все новые файлы останутся без строк в БД. При успешной замене или удалении материала прежние файлы удаляются только после изменения БД, а ошибки `unlink` полностью игнорируются. Аварийный выход между этими операциями также оставляет сирот. Каскадное удаление `Attachment` при удалении родительских сущностей вообще не вызывает очистку диска.
- **Место:** `src/server/files.ts:48-60` (частичная запись без отката), `src/server/files.ts:68-70` (игнорирование всех ошибок удаления), `src/server/repos/homework.ts:27-34`, `src/server/repos/homework.ts:60-68`, `src/server/repos/homework.ts:148-157`, `src/server/repos/homework.ts:37-42`, `prisma/schema.prisma:501-516`.
- **Предложение по исправлению:** сохранять список уже записанных ключей и удалять его в `catch` при неудачной загрузке/создании; прежние файлы удалять только после успешного коммита. Ошибки удаления логировать и добавить периодическую сверку `storageKey` в БД с файлами на диске с безопасной отложенной очисткой. Не пытаться откатывать БД ради уже удалённого файла: основой должна быть консистентность метаданных плюс восстанавливаемая очистка.

### 5. Проверка типа файла выполняется только по расширению

- **Серьёзность:** средняя.
- **Почему это проблема:** произвольное содержимое можно назвать `solution.pdf` или `macro.doc`, и оно пройдёт проверку. Поле `mime` затем также назначается по расширению, а не по фактическому содержимому. `Content-Disposition: attachment` и `nosniff` уменьшают риск исполнения в браузере, но не защищают пользователя от вредоносного документа, макроса или файла, который не открывается заявленной программой.
- **Место:** `src/server/files.ts:18-27`, `src/server/files.ts:33-45`, `src/server/files.ts:54-59`; смягчающая отдача — `src/app/api/files/[id]/route.ts:15-23`.
- **Предложение по исправлению:** проверять сигнатуры PDF и OLE2, для OOXML — ZIP-структуру и обязательные элементы пакета; затем повторно проверять ограничения размера. При необходимости добавить антивирусное сканирование отдельным этапом. Тесты должны включать исполняемый файл, переименованный в `.pdf`, HTML под видом `.docx` и хотя бы по одному настоящему файлу каждого разрешённого семейства.

### 6. Уведомления о ДЗ неидемпотентны; общий дефект повторного push из аудита 17.11 сохраняется

- **Серьёзность:** средняя.
- **Почему это проблема:** повторный вызов проверки с тем же статусом снова обновляет сдачу и создаёт новое уведомление с push — `dedupeKey` не передаётся. Создание материала/задания также выполняется до уведомления: если запись уведомления упадёт, клиент получит ошибку после уже сохранённой сущности и может создать дубль при повторной попытке. Кроме того, `notify()` применяет `skipDuplicates` только к строкам в БД, но вызывает `sendPush` для всех переданных пользователей независимо от фактической вставки. Это тот же дефект, что описан в п. 2 `docs/security-audit-2026-11-17.md`; по `src/server/notify.ts` он не исправлен.
- **Место:** `src/server/repos/homework.ts:29-34`, `src/server/repos/homework.ts:62-68`, `src/server/repos/homework.ts:92-98`, `src/server/notify.ts:7-15`, `src/server/notify.ts:32-53`, `docs/security-audit-2026-11-17.md:49-60`.
- **Предложение по исправлению:** сделать повторную проверку той же версии идемпотентной и возвращать текущее состояние без нового уведомления. Для новых сущностей использовать `dedupeKey` с их `id`, для проверки — с `id` и версией сдачи. Изменить `notify`, чтобы push уходил только получателям реально вставленных уведомлений. Состояние и запись уведомления сохранять атомарно, а внешний push запускать после коммита. Повторные HTTP-запросы и сбой после сохранения сущности покрыть тестами.

Уточнение: `remindDeadlines()` читает модель `Deadline`, а не `Assignment`, поэтому отдельного автоматического спама уведомлениями о ДЗ при каждой загрузке главной в текущем коде нет. Для существующих вызовов ДЗ проблема относится к повторным действиям и к общему механизму push.

### 7. Сдача после срока всегда разрешена — это политика, а не техническое ограничение

- **Серьёзность:** низкая.
- **Почему это проблема:** студент может отправить работу в любой момент после `dueAt`; сервер даже не загружает срок при сдаче. Интерфейс явно обещает «Сдать ещё можно», а преподаватель видит пометку «позже срока». Если команда ожидает жёсткий дедлайн, текущее поведение ему не соответствует. Повторная сдача также меняет `submittedAt`, поэтому видна только дата последней версии, а не история первой и последующих сдач.
- **Место:** `src/server/repos/homework.ts:111-116`, `src/server/repos/homework.ts:142-155`, `src/app/(student)/homework/[id]/page.tsx:19`, `src/app/(student)/homework/[id]/page.tsx:74-76`, `src/lib/homework.ts:5-9`.
- **Предложение по исправлению:** подтвердить продуктовое решение. Для жёсткого срока проверять `dueAt` в репозитории, а не только скрывать форму. Если поздняя сдача разрешена, оставить текущее поведение, но явно зафиксировать правило; для аналитики «первая сдача вовремя / с опозданием» хранить историю попыток.

### 8. Доступ преподавателя не ограничен текущим периодом преподавания

- **Серьёзность:** низкая.
- **Почему это проблема:** `teachesPair` проверяет наличие любой пары преподавателя в группе по дисциплине за всю историю. Преподаватель прошлого семестра сохраняет возможность читать новые студенческие файлы, удалять материалы и проверять новые сдачи этой дисциплины. Для действующего совместного преподавания это может быть осознанным правилом, но для смены преподавателя — лишним доступом.
- **Место:** `src/server/repos/teacher.ts:31-33`, `src/server/files.ts:92-95`, `src/server/repos/homework.ts:18-20`, `src/server/repos/homework.ts:37-42`, `src/server/repos/homework.ts:86-99`.
- **Предложение по исправлению:** ввести явное назначение преподавателя на дисциплину/семестр или ограничивать область актуальным учебным периодом. Отдельно решить, может ли коллега по той же дисциплине удалять чужой материал: сейчас проверяется дисциплина, а не `Material.teacherId`.

### 9. API преподавателя проверяет наличие профиля, но не роль пользователя

- **Серьёзность:** низкая.
- **Почему это проблема:** маршруты создания задания и добавления/удаления материала пропускают любого пользователя с заполненной связью `user.teacher`, не проверяя `user.role === TEACHER`. В текущей схеме роль и связь независимы. Если при изменении аккаунта возникнет пользователь с ролью `STAFF` или `STUDENT` и сохранившейся связью `Teacher`, он сможет выполнять эти операции в пределах `teachesPair`. Страницы и действие проверки используют более строгий `requireTeacher`.
- **Место:** `src/app/api/teacher/assignments/route.ts:21-24`, `src/app/api/teacher/materials/route.ts:20-23`, `src/app/api/teacher/materials/[id]/route.ts:6-10`, `src/server/auth.ts:104-110`, `prisma/schema.prisma:80-94`.
- **Предложение по исправлению:** добавить общий `apiTeacher`, который проверяет и роль, и профиль, и использовать его во всех `/api/teacher/*`. Добавить тест с несоответствующей ролью и связью.

### 10. Имена файлов очищены от путей, но не от визуально обманчивых Unicode-символов

- **Серьёзность:** низкая.
- **Почему это проблема:** кириллица сохраняется корректно в имени, путь и ASCII-управляющие символы удаляются. Однако Unicode-символы двунаправленного управления и невидимые символы остаются: имя может визуально искажать порядок букв и расширение в списке файлов. Отдельно корректность заголовка `filename*` для всех сочетаний апострофов, `*` и неASCII-символов зависит от точного RFC 5987-кодирования и браузера.
- **Место:** `src/server/files.ts:33-39`, `src/app/api/files/[id]/route.ts:16-22`.
- **Предложение по исправлению:** дополнительно удалять bidi-управляющие и невидимые символы, нормализовать Unicode, сохранять безопасное ASCII-имя как `filename` и корректно кодировать `filename*` по RFC 5987. Добавить тесты на кириллицу, пути, апострофы, `%`, bidi и длинные имена.

## Что проверено и выглядит надёжным

- **Студент не получает чужое задание:** список и детальная выборка ограничены `groupId` из сессии (`src/server/repos/homework.ts:118-136`); сдача чужого задания отклоняется до записи файлов (`src/server/repos/homework.ts:142-148`).
- **Студент не получает чужую сдачу:** в детальную выборку включены только `submissions` с его `studentId`; скачивание чужой сдачи запрещено даже при знании `attachmentId` (`src/server/files.ts:75-91`).
- **Деканат не скачивает файлы студентов:** `canAccessAttachment` не имеет разрешающей ветки для `STAFF` и возвращает `null`; маршрут превращает это в одинаковый 404 (`src/server/files.ts:88-96`, `src/app/api/files/[id]/route.ts:7-14`).
- **Чужая группа/дисциплина преподавателя отсекается:** список, создание, получение, проверка и удаление материала используют `teachesPair`; создание проверяет доступ до сохранения файлов (`src/server/repos/homework.ts:18-30`, `src/server/repos/homework.ts:45-99`).
- **Обычные переходы статусов соответствуют интерфейсу:** принятая работа не может быть заменена при отсутствии гонки; `RETURNED` разрешает новую отправку, которая снова ставит `SUBMITTED`, очищает старую рецензию и заменяет вложения (`src/server/repos/homework.ts:141-158`). Поздняя отправка помечается по `submittedAt > dueAt`.
- **Замена вложений в БД транзакционна:** удаление прежних строк `Attachment` и `upsert` находятся в одной транзакции, а физическое удаление прежних файлов выполняется только после неё (`src/server/repos/homework.ts:149-157`).
- **Обычное удаление материала последовательно правильное:** сначала проверяется доступ, затем одной операцией удаляется материал с каскадными метаданными вложений, после чего делается попытка удалить файлы (`src/server/repos/homework.ts:37-42`). Сбои этой попытки описаны в находке 4.
- **Лимиты реализованы на сервере:** максимум 10 МБ на файл, 5 файлов и 25 МБ суммарно; проверяются все файлы до начала записи (`src/server/files.ts:12-15`, `src/server/files.ts:41-60`). Дополнительно задан лимит прокси 26 МБ (`next.config.ts:8-9`).
- **Хранение и скачивание используют безопасные базовые меры:** случайный 36-символьный hex-ключ, строгая проверка ключа перед чтением, исходное имя не участвует в пути, скачивание только как attachment с `nosniff` и `private, no-store` (`src/server/files.ts:29-39`, `src/server/files.ts:56-69`, `src/app/api/files/[id]/route.ts:13-23`).
- **Кириллица и стандартные спецсимволы имени обрабатываются предусмотрительно:** путь отбрасывается, запрещённые Windows-символы заменяются, имя ограничено 120 символами и кодируется для Content-Disposition (`src/server/files.ts:35-39`, `src/app/api/files/[id]/route.ts:20`). Оставшиеся Unicode-риски описаны отдельно.

6. **Доступ на HTTP-уровне:** неавторизованный запрос, несовпадающая роль/профиль, неотличимый 404 и заголовки скачивания.
7. **Уведомления:** количество записей и push при повторных действиях, ошибка после создания сущности, отсутствие уведомления отправителю и дедупликация.
8. **Вложения задания:** отдельный тест `canAccessAttachment` для файла условия задания; сейчас явно проверяются материал и сдача.

## Что нельзя проверить без запуска и почему

- **Фактические параллельные сценарии и поведение Prisma upsert при уникальном конфликте:** порядок транзакций зависит от БД и планировщика запросов; статически подтверждено отсутствие синхронизации, но воспроизведение нужно для регрессионных тестов.
- **Сбои диска и процесса:** отсутствие места, права на запись, частичную запись и остановку между коммитом и `unlink` невозможно подтвердить чтением.
- **Настоящие документы и сигнатуры:** валидность PDF/OLE2/OOXML и поведение макросов требуют реальных файлов и их обработки.
- **HTTP-интеграция:** реальные статусы после middleware/proxy, ограничение 26 МБ до `req.formData()`, потребление памяти multipart и поведение Next.js Route Handlers нужно проверять запросами.
- **Content-Disposition в браузерах:** итоговое имя файла с кириллицей и спецсимволами зависит от браузера и HTTP-стека.
- **Уведомления и push:** фактическое число доставок, поведение нескольких устройств, ошибки push-провайдера и дедупликация требуют тестового окружения.
- **UI-сценарии:** отображение новой версии после `router.refresh()`, блокировки кнопок и восприятие статусов без браузера не проверялись.
