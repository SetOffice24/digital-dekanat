## Контекст проекта

- Прототип личного кабинета студента для конкурса. Вымышленный вуз «Универ», все данные вымышленные. Пометка «концепт для конкурса» — обязательна.
- Стек: Next.js 16.4 (App Router, `src/proxy.ts` вместо middleware) · React 19 · Tailwind 4 · Prisma 6 + PostgreSQL 16 · argon2id · pdf-lib + qrcode · PWA + Web Push (VAPID) · Docker Compose + Caddy.
- Роли: `STUDENT`, `STAFF`, `TEACHER`. Данные — только через репозитории `src/server/repos/*` с фильтром по сущности из сессии; чужой id → неотличимый 404. Это Правило №2 проекта (см. `docs/ARCHITECTURE.md` §3.2, `CLAUDE.md`).
- Это прототип под демо жюри: часть упрощений осознанна (in-memory счётчики, нет CSP и т.п.). Ниже каждая находка помечена: **баг** (чинить однозначно), **усиление** (стоит поправить), **осознанный компромисс** (обсуждать с командой, не чинить молча).

## Подробные находки

### 1. Демо-вход без пароля по умолчанию — [Компромисс деплоя]

**Где:** `src/app/login/actions.ts:41-49` (`demoLoginAction`), `deploy/.env.example:11` (`DEMO_LOGIN=1`).

**Что:** любой посетитель сайта в один клик входит в 4 тестовых аккаунта, включая `dekanat` (выдача справок, перенос пар, объявления) и `teacher`. Выключение — только если в `deploy/.env` на сервере явно `DEMO_LOGIN=0`.

**Почему это важно:** после публикации по инструкции из README/HANDOFF флаг останется включённым. Забыть выключить после презентации — одна строчка в чек-листе деплоя.

**Варианты:**
- Минимум: пункт «после демо жюри поставить `DEMO_LOGIN=0` и пересоздать контейнер» в чек-лист деплоя (`deploy/deploy.sh` выводит напоминание, если `DEMO_LOGIN != 0`).
- Усиление: разрешить демо-вход только для `NODE_ENV !== "production"` или по отдельному флагу `DEMO_LOGIN=1` вручную на время презентации.

**Обсуждение:** для конкурса кнопки нужны (вход жюри за 10 секунд). Риск операционный, а не кодовый.

### 2. Push-уведомления о дедлайнах — спам при каждой загрузке главной — [Баг]

**Где:** `src/server/notify.ts:7-15` (`notify`), `src/server/notify.ts:32-53` (`remindDeadlines`), вызов — `src/app/(student)/page.tsx:31`.

**Что:** `notify()` делает `createMany({ skipDuplicates: true })` — дедупликация работает только на записи в БД, — но `sendPush()` вызывается безусловно. `remindDeadlines()` исполняется при каждом рендере «Моего дня». Итог: каждое открытие/обновление главной шлёт студенту push по каждому дедлайну в ближайшие 3 дня.

**Исправление:** вернуть из `createMany` результат и слать push только по реально вставленным записям. Примерный план:
1. В `notify()`: `const res = await prisma.notification.createMany(...)`; `createMany` в Prisma не возвращает id вставленных строк — поэтому надёжнее перед вставкой сделать `findMany({ where: { userId: { in: userIds }, dedupeKey: n.dedupeKey } })`, вычислить, у кого записи ещё нет, и слать push только им.
2. Альтернатива без лишнего запроса: для дедлайнов вести отдельную таблицу отправленных напоминаний — избыточно для прототипа.
3. После исправления: обновить `docs/process-log.md` (правило проекта — журналировать значимые шаги).

**Проверка:** включить push в браузере, создать дедлайн в сиде, 3 раза обновить `/` — должен прийти ровно один push.

### 3. Перепривязка чужой push-подписки — [Баг/усиление]

**Где:** `src/server/push.ts:45-55` (`savePushSubscription`).

**Что:** `upsert({ where: { endpoint }, update: { userId, ... } })` — если endpoint уже закреплён за другим пользователем, запись перезаписывается. Endpoint — bearer-секрет устройства; узнав его, злоумышленник перенаправит чужие push-уведомления себе.

**Исправление:** если существующая подписка принадлежит другому `userId` — не перепривязывать (вернуть `false` или удалить старую и создать новую — но удаление чужой при подтверждённом владении endpoint всё равно спорно). Практичный вариант: оставить upsert только когда `userId` совпадает, иначе молча успех без изменений. Учесть легитимный сценарий «на одном устройстве два аккаунта по очереди» — тогда вторая подписка того же браузера должна заменять первую; компромисс: при смене владельца удалять старую запись и создавать новую (итог тот же, но явный).

**Тест:** добавить в `tests/push.test.ts`: подписка A на endpoint E, затем подписка B на тот же E → старое поведение (перепривязка) против нового.

### 4. Лимит попыток входа обходится поддельным XFF — [Усиление]

**Где:** `src/app/login/actions.ts:21` — `h.get("x-forwarded-for")?.split(",")[0].trim()`.

**Что:** берётся первое значение `x-forwarded-for`. Caddy дополняет заголовок, не перезаписывая, так что клиентский фейк оказывается первым → счётчик лимита легко сбрасывается. Плюс лимит только по паре `login|ip`: нет глобального лимита на IP. Счётчик in-memory — сброс при рестарте (это осознанно, см. ARCHITECTURE §3.1).

**Исправление:**
- IP брать из последнего значения XFF (IP непосредственного пира — Caddy) или из `x-real-ip`, если Caddy его ставит; идеальнее — доверять только `x-forwarded-for` от прокси и в dev брать socket-адрес.
- Добавить второй счётчик: N попыток в окно на один IP независимо от логина (защита от перебора множества аккаунтов).

### 5. CSRF-проверка в proxy обходится — [Усиление]

**Где:** `src/proxy.ts:13-19`.

**Что:**
- Запросы без заголовка `Origin` проверку проходят мимо (`if (origin && host && ...)`).
- Сверка идёт с `x-forwarded-host`, который клиент может подставить равным своему Origin.

**Смягчающие обстоятельства:** cookie `SameSite=Lax` (cross-site POST fetch без cookie → 401) и встроенная проверка Origin у Next.js Server Actions. Так что реальная атака маловероятна, но заявленная в ARCHITECTURE §3.3 «проверка Origin в middleware» как единственная мера — слабая.

**Исправление:** для не-GET запросов к `/api/*` без `Origin` — 403 (браузерные формы/fetch с cookie всегда шлют Origin на cross-site; собственные скрипты шлют). Сверять `Origin` со значением `Host`, а `x-forwarded-host` учитывать только если он совпадает с `Host` или приходит от доверенного прокси. Проверить поведение Caddy: какой заголовок хоста реально доходит до app.

### 6. Файлы проверяются только по расширению имени — [Усиление]

**Где:** `src/server/files.ts:33-45` (`ext`, `checkFile`).

**Что:** принимается любое содержимое, если имя заканчивается на `.pdf/.doc(x)/.xls(x)/.ppt(x)`. Отдача с `Content-Disposition: attachment` + `nosniff` (`src/app/api/files/[id]/route.ts:16-24`) блокирует XSS через polyglot-HTML, но вредоносный PDF/документ с макросами дойдёт до скачивания.

**Исправление:** проверка magic bytes первых килобайтов по белому списку (PDF: `%PDF-`; docx/xlsx/pptx: ZIP `PK\x03\x04` + наличие `[Content_Types].xml` в начале архива; doc/xls/ppt: OLE2 `\xd0\xcf\x11\xe0`). Для прототипа достаточно проверки сигнатуры первых 8 байт без распаковки ZIP. Отклонённые файлы — с понятной ошибкой (уже есть механизм `UploadError`).

### 7. Прямые вызовы `prisma` вне репозиториев — [Архитектура]

**Где:**
- `src/app/verify/[code]/page.tsx:15` — публичная проверка справки (по `verifyCode`, без сессии);
- `src/app/(student)/layout.tsx:7` — `group.findUnique` для имени группы;
- `src/app/api/notifications/unread/route.ts:12` — выборка последнего уведомления;
- `src/app/(student)/requests/actions.ts:16` — `requestType.findUnique`;
- `src/app/(student)/assistant-actions.ts:23` — `request.findFirst` для пометки черновика.

**Что:** нарушение собственного Правила №2 (ARCHITECTURE §3.2) «Prisma только в `src/server/repos`». Запросы параметризованы, инъекций нет, но: grep-линт из ARCHITECTURE §10 этих мест не видит; прецедент размножается.

**Исправление:** перенести выборки в `src/server/repos/*` (для verify — в новый `repos/verify.ts` или в существующий, но без session-фильтра, с комментарием «публичный метод»). Обновить архитектурный grep-тест, если он есть (`tests/` — посмотреть, есть ли линт-тест).

### 8. Необработанный ZodError в server actions — [Баг]

**Где:**
- `src/app/(student)/requests/actions.ts:43` — `z.string().max(40).parse(id)` без `.min(1)` и без try/catch;
- `src/app/(student)/student-actions.ts:10` — `.parse(mood)`;
- `src/app/(student)/student-actions.ts:16` — `.parse(id)`.

**Что:** пустой/невалидный аргумент → неперехваченный `ZodError` → 500 вместо 400/понятной ошибки. На UI не отражается (клиент шлёт валидные данные), но любая ручная подмена запроса даёт 500-ю страницу.

**Исправление:** `.safeParse` + ветка ошибки, как в соседних экшенах.

### 9. Нет валидации переходов статусов заявки — [Баг бизнес-логики]

**Где:** `src/server/repos/staff.ts:124,134-162` (`STAFF_STATUSES`, `changeRequestStatus`).

**Что:** допустим любой переход между `IN_REVIEW/NEED_INFO/READY/DONE/REJECTED`, включая абсурдные (`DONE → IN_REVIEW`, `REJECTED → READY`) и повторную выдачу сертификата (защита от дубля сертификата есть: `!r.certificate`). Конкурентные смены статуса — «последняя запись побеждает».

**Исправление:** таблица допустимых переходов, например: `NEW/IN_REVIEW/NEED_INFO → IN_REVIEW | NEED_INFO | READY | REJECTED`; `READY → DONE | REJECTED`; терминальные `DONE/REJECTED` — без переходов. Проверять в `changeRequestStatus` до записи, возвращать понятную ошибку. Если команда решит, что свобода деканату нужна — зафиксировать решение в `docs/process-log.md`.

### 10. Приём ДЗ после дедлайна и сироты файлов — [Компромисс]

**Где:** `src/server/repos/homework.ts:142-159` (`submitHomework`).

**Что:** дедлайн не проверяется — поздняя сдача принимается (у преподавателя пометка «позже срока», вероятно осознанно). Файлы пишутся на диск до транзакции — при её сбое остаются сиротами. При двух параллельных сдачах возможна гонка: обе прочитают `prev`, вторая перезапишет файлы первой (файлы первой станут сиротами на диске).

**Исправление (минимум):** вынести `storeFiles` после проверок внутрь транзакции нельзя (диск в транзакции не откатывается) — вместо этого: 1) удалять сирот по расписанию (скрипт/крон) или 2) принимать как есть, т.к. объём ограничен. Если сдача после дедлайна нежелательна — добавить проверку `dueAt` с флагом «принимать, но помечать» (сейчас пометка уже есть у преподавателя).

### 11. `teachesPair` — вечный доступ к группе — [Компромисс]

**Где:** `src/server/repos/teacher.ts:31-33`.

**Что:** доступ определяется наличием любой пары преподаватель↔группа↔дисциплина за всю историю. После окончания семестра доступ сохраняется.

**Исправление:** если потребуется — ограничить текущим семестром (по датам пар), но для прототипа с сидом это избыточно. Оставить как есть, отметить в документации.

### 12. Нет CSP и HSTS — [Усиление]

**Где:** `next.config.ts:18-30` (заголовки есть: X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy), `deploy/Caddyfile`.

**Что:** нет Content-Security-Policy и Strict-Transport-Security.

**Исправление:** HSTS — одна строка в Caddyfile (`header Strict-Transport-Security "max-age=31536000"`). CSP для Next-приложения собирать осторожно (inline-скрипт темы в `src/app/layout.tsx:31` требует nonce или хэша; есть `script-src 'unsafe-inline'` минимум для первой загрузки). Для прототипа приоритет низкий; если делать — сначала в report-only режиме.

### 13. Сессии — нет продления и глобального logout — [Компромисс]

**Где:** `src/server/auth.ts:57-89`.

**Что:** сессия живёт фиксированные 30 дней без скользящего продления; записи истёкших сессий не удаляются (таблица растёт — некритично); logout удаляет только текущую сессию — другие устройства остаются активными; нет «выйти везде».

**Исправление:** по желанию команды: sliding renewal при `getCurrentUser`, периодическая чистка истёкших, кнопка «выйти со всех устройств» в профиле. Для прототипа — не нужно.

## Проверено и признано в порядке

Чтобы не дублировать работу — эти места проверены, находок нет:

- **AuthN:** argon2id + `dummyHash` для выравнивания таймингов (`auth.ts:27`), единая формулировка ошибки входа, session id = `randomBytes(32)` base64url, cookie `httpOnly`/`Secure` (зависит от `APP_URL`, в проде за Caddy — https)/`SameSite=Lax`.
- **AuthZ/IDOR:** все выборки в репозиториях фильтруются по сущности из сессии; чужой id → 404; факультетская область сотрудника соблюдается (`studentScope`/`groupScope` в `repos/staff.ts`); преподаватель — только свои пары; подгруппы учитываются.
- **XSS:** весь пользовательский контент (ответы ИИ, объявления, уведомления, комментарии, ФИО) рендерится через React-экранирование; markdown не превращается в HTML; единственный `dangerouslySetInnerHTML` — статический скрипт темы (`layout.tsx:31`).
- **ИИ-контур:** контекст студента собирается сервером только по своему `studentId` (`ai/context.ts`); черновики валидируются Zod-схемами полей типа (`assistant.ts:112-124`); фраза посещаемости помечена «данные, не инструкции», чужие id отбрасываются (`ai/attendance.ts:78-80`); таймаут 30 с и откат на rules; rate limit 20 сообщений/10 мин на студента; промпт-инъекция раскрывает максимум собственные данные студента.
- **Файлы:** случайные storageKey (`randomBytes(18)`), скачивание только через `/api/files/[id]` с ролевой проверкой `canAccessAttachment`; деканат файлов студентов не видит; отдача `attachment` + `nosniff`; лимиты 5 файлов/25 МБ на запрос, 10 МБ на файл.
- **Справки:** `verifyCode` — 12 символов из 32-символьного алфавита без похожих знаков (`repos/staff.ts:18`), перебор неосуществим; публичная `/verify/[code]` показывает минимум PII; дубль сертификата заявке не выдаётся.
- **ICS:** экранирование `\\;,` и переводов строк (`api/schedule/ics/route.ts:7`).
- **Секреты:** `.env`/`.env.*` в `.gitignore` и `.dockerignore`, в git только пустые `.env.example`; VAPID генерируются на сервере `deploy/deploy.sh`, в git не попадают; ключ ИИ — только на сервере, браузер ходит на `/api/assistant`.
- **SQLi:** весь доступ через Prisma, параметризован.
- **Web Push:** endpoint только `https`, формат ключей и длины проверяются, DELETE подписки — только своя (`api/push/route.ts`).
- **Тесты:** 43 теста (`tests/`: authz, teacher, staff-search, bulk-preview, attendance, push, homework) покрывают IDOR-границы.

## Правила проекта (для ИИ, который будет вносить правки)

1. Сначала прочитать `docs/HANDOFF.md` и `CLAUDE.md`; сверяться с `docs/00-tz.md`.
2. Общаться с командой на русском; в коде — без лишних комментариев (стиль файла важнее своих привычек).
3. Каждый запрос к данным — через `src/server/repos/*`, фильтр по сессии; чужое → 404/403.
4. Только вымышленные данные; пометка «концепт для конкурса» никуда не девается.
5. Mobile-first: проверять на 360 px; визуал проверять глазами в браузере, не только тестами.
6. После значимого шага — запись в `docs/process-log.md` (задача, модель, ключевой промпт, результат, ошибки ИИ). Это половина оценки критерия «нейротехнологии».
7. Проверки: `corepack pnpm exec tsc --noEmit`, `corepack pnpm lint`, `corepack pnpm test` (нужна засеянная БД: `corepack pnpm db:local` + `prisma migrate deploy` + `db:seed`).
8. Push на GitHub и действия на VPS — только по явной команде пользователя.
9. Новые разделы/библиотеки — только с согласования команды; версии зафиксированы, не обновлять.
