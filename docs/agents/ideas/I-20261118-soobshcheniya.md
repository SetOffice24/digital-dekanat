## Проблема

Сейчас студент может «поговорить» с деканатом только внутри заявки (деканат задаёт вопрос — студент отвечает), а с преподавателем — никак. Преподаватель не может написать студенту, деканат — преподавателю. Команда: «студенты, преподаватели и деканат должны писать друг другу».

## Предложение

**Кто кому пишет**

| Отправитель → получатель | Можно | Как |
|---|---|---|
| Студент → деканат | да | Деканату как отделу; видят все сотрудники деканата его факультета; видно, кто ответил |
| Студент → преподаватель | только своих дисциплин | Личный диалог |
| Преподаватель → студент | только из своих групп | Личный диалог |
| Преподаватель → деканат | да | Деканату как отделу |
| Деканат → студент / преподаватель | в пределах своего факультета | Личный диалог от имени деканата |
| Студент → студент | нет | Без спама и модерации |

Групповых чатов (преподаватель + вся группа) в этой версии нет — решение команды 18.11; для массовых сообщений есть объявления.

**Возможности диалога**
- Текст и файлы (Word, PDF, Excel, PowerPoint — то же хранилище и проверки, что у ДЗ).
- Привязка к поводу: диалог можно начать из заявки, дисциплины или задания — вверху «по заявке № 75» / «по Лабораторной №5» со ссылкой.
- Прочитано / не прочитано; новые сообщения появляются без перезагрузки (опрос, как у уведомлений) и приходят уведомлением + push.
- Обращения в деканат: статус «открыто / решено»; решённые — в архив; ответ студента открывает обращение снова.

**Интерфейс**
- У всех ролей — значок «Сообщения» в шапке рядом с колокольчиком со счётчиком непрочитанных (меню не меняется; у студента остаётся 4 раздела).
- Экран сообщений: слева список диалогов (поиск по имени, непрочитанные сверху), справа переписка; на телефоне — список, затем диалог.
- Кнопки «Написать»: студент — в дисциплине, задании, заявке; преподаватель — в журнале и карточке студента; деканат — в личном деле и карточке заявки.
- Деканат — общие входящие обращения с фильтрами «новые / в работе / решённые».

**Данные (новые таблицы):** диалог (тип: личный / обращение в деканат; повод: заявка / дисциплина / задание; статус обращения; факультет для маршрутизации), участник, сообщение, вложение (через существующую `Attachment`), отметка прочтения.

## Ценность и соответствие проекту

Прямая связь участников учёбы — одна из главных болей, которые закрывает «цифровой деканат»; уменьшает визиты и звонки в деканат. Использует уже готовые уведомления, push и безопасное хранилище файлов.

## Альтернативы

- Свободный мессенджер «всем со всеми» — модерация, спам, нет повода переписки; отклонено.
- Только переписка внутри заявок (как сейчас) — не покрывает преподавателя и вопросы без заявки.
- Внешний мессенджер / почта — данные уходят из системы, нет связи с заявками и ДЗ.

## Риски и ограничения

- **Права** — главный риск: сервер на каждое действие проверяет, что пара ролей допустима и пользователь — участник диалога; чужой диалог → 404; сотрудник видит только обращения своего факультета. Тесты на каждую пару ролей.
- Злоупотребления: ограничение частоты сообщений, длина текста, только текст (без HTML), файлы — существующие лимиты.
- Уведомления: push только по реально новым сообщениям (не повторять ошибку дедлайнов из `docs/security-audit-2026-11-17.md`, п. 2).
- Опрос без WebSocket — задержка до ~10 с; для прототипа достаточно.
- Новые таблицы → миграция, `prisma generate` (остановка dev-сервера), пересев демо-данных — координировать с другими агентами.
- 360 px: экран диалога и поле ввода над нижней панелью студента.

## Критерии проверки

- Сценарии: студент → преподаватель своей дисциплины (и отказ для чужого); студент → деканат, ответ сотрудника, «решено», повторное открытие; преподаватель → деканат; деканат → студент из личного дела; файл в сообщении; счётчик и push у получателя.
- Чужой диалог и чужое вложение — 404; студент не может написать студенту.
- 360 px и широкий экран, без горизонтальной прокрутки.

## Вопросы к участникам

1. Модель данных: достаточно ли одной таблицы диалогов с типом и поводом, или обращения в деканат лучше отдельной сущностью?
2. Как надёжнее маршрутизировать обращения: по факультету студента или назначать конкретного сотрудника?
3. Какие ещё злоупотребления или утечки данных возможны в предложенной схеме прав?
4. Что из существующего (вопрос деканата в заявке `NEED_INFO`) стоит перевести на новые сообщения, а что оставить как есть?
